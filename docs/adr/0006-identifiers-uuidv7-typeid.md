# ADR-0006: UUIDv7 primary keys, TypeID public identifiers

- Status: Proposed
- Date: 2026-09-24

## Context

IDs appear in URLs, APIs, webhooks and logs. Sequential integers leak
volumes and invite enumeration. Random UUIDv4 hurts B-tree locality at scale.

## Decision

- Primary keys: **UUIDv7**, generated by the application (Prisma
  `uuid(7)`), stored in native `uuid` columns.
- Public representation: **TypeID**, `<prefix>_<base32(uuid)>` (e.g.
  `prod_01j9…`). It is a reversible encoding of the same UUID, not an extra
  column. Prefixes are listed in `docs/api/README.md`. Decoding validates the
  prefix, so a product ID can't be passed where an order ID is expected.
- Branded TypeScript types (`ProductId`, `StoreId`, …) in `packages/types`.
- Human-facing sequence numbers exist only where merchants expect them
  (`Order.orderNumber`, per store).

## Consequences

- Time-ordered inserts, no enumeration, globally unique across tenants
  (helps exports, merges, sharding).
- UUIDv7 reveals the creation timestamp. This is acceptable for our
  resources.
- A small codec layer at API/URL boundaries.

## Alternatives considered

Bigint sequences + hashids (reversible obfuscation, coordination needed
across shards); UUIDv4 (poor locality); CUID2 (text keys, larger indexes).
